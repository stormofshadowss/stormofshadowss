## Packing checklist (migration 005)
Each parcel in the queue has a saved checklist: every item ticked off (`parcel_items.packed_at`), plus the delivery address, the Lomo name (when the parcel has one) and
the bias name (when given) confirmed (`parcels.*_checked_at`). `POST /api/admin/parcels/:id/items-packed {packed, claimIds?}` and `/checks {address?, lomo?, bias?}` save ticks
as they're made (only while the parcel is in the queue); **`/packed` is refused (409 `checklist_incomplete`, naming what's missing) until everything applicable is ticked**, and the
Mark packed button is disabled until then. The screen updates ticks in place without redrawing, so typed fees are never lost. Tests tick via `tickParcel()` in `test/helpers.js`.

## Rules that must not be broken (each came from a real bug or a decision)
- **Money:** `DECIMAL(10,2)`; credit balance = SUM of `credit_ledger.balance_effect` (never a stored number); a cost line is never overpaid
  (excess → credit); splits use `splitAmount` (penny-exact). Overpayment: the *joiner* chooses credit or tip when paying.
- **Locking:** every flow touching a person's money locks the **joiner row first**, then claims/cost rows, in ascending id order; transactions run
  `READ COMMITTED` with deadlock retry (`db.js withTx`). A stress test (24 simultaneous requests) guards this.
- **Cancel:** `lib/cancel.js` — paid amounts return as credit, except blocked handles (recorded `forfeited`, balance effect 0). Never cancel a claim that is in an active parcel.
- **Sign-in:** claim with handle only (a new handle's first browser gets a `sos_device` proof cookie → can link its email with no approval; GOM approval is only the rare fallback; GOM reviews new links after the fact and can mark handles verified, which the packing queue flags); email link needs a POST button (scanners); links hashed + single use; handle with stake needs GOM approval;
  admin accounts can never use email links. All state-changing API calls need `X-Requested-With: sos`.
- **Preview decisions:** no PIN; no payment processing; UK dates (dd/mm/yyyy shown, ISO stored); palette in the preview's CSS variables;
  no server-side basket holds (set slots are only taken at submit; the shop preview is advisory); a fixed claimer leaving a secured all-parts set leaves a hole for the GOM to fill.
- **Sets:** a set holds one of each part; repeats spread across sets; part prices via `item_members.price`; `requires_full_set` blocks securing until full;
  two people fixed on one member land in different sets and other fixed members pack into the same early sets.

## Screen conventions (follow these in every new tab)
`GOM.registerTab({id,label,render})` in a new `public/gom/<name>.js`, add its `<script>` to `admin.html` before `boot.js`. Assign `el.onclick/onsubmit/onchange`
(not addEventListener — the tab body element is reused). Always `esc()` anything from the database. Dialogs via `GOM.confirm/alert`, messages via `GOM.toast`
or an inline `[data-msg]` in the form — **never** the browser's alert/confirm/prompt. Dates stored ISO, shown with `GOM.fmtDate` (dd/mm/yyyy). Remember UI state
(open accordions, filters) across redraws. Every screen gets jsdom tests that check the result through the API.

## Working method
Small, tested steps. Write tests against the real DB first-class (`server/test/*.test.js`, helpers in `test/helpers.js`: `startApp`, `adminLogin`, `login`,
`seed`, `claimAndSecure`, `joinerSession`). Test what the screens do with jsdom against the real API before packaging. End every stage with: all tests green,
zip rebuilt, this file updated.

## Known limits (deliberately left out, or not yet verified in real use)
- **Never run against real services:** Docker/Unraid deployment, a real SMTP server (notification + sign-in emails), Cloudflare Tunnel, and a real iPhone uploading a HEIC photo. Everything else is tested against a real MariaDB with 895 tests.
- **Not reviewed visually:** every screen was tested for behaviour in a simulated browser, not looked at on a phone. Expect small layout fixes.
- **One intermittent test failure was seen once** (a clean-unzip run with 1 of 350 failing) and never reproduced in ~20 later runs; the failing test was never identified. If a test ever fails in CI, keep the full log.
- Shop stock: one price/quantity per item (no size/colour variants). Pictures: one per item (no gallery). Notifications: a single on/off switch (no per-event choices), plain-text emails.
- A proxy payment for an ordinary item covers claims by COUNT (a cancelled claim's paid-for unit is reused by the next claim).
- The Claims tab's bulk move deliberately excludes stages driven by other screens (boxes, packing, shipping).
